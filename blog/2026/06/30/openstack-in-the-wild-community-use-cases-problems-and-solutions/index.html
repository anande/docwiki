    OpenStack in the Wild: Community Use Cases, Problems, and Solutions¶

    A curated catalogue of real-world OpenStack deployments drawn from the openstack-discuss mailing list, r/openstack, OpenInfra Foundation user stories, and production write-ups. Each entry covers the use case, the problems encountered, and the solutions that worked. As of October 2025, OpenStack's global footprint exceeds 55 million compute cores across thousands of production deployments.

    1. Hyperscale Private Cloud¶

    Walmart — 1 Million+ Cores¶
    Scale 1,000,000+ compute cores across multiple data centres
    Team Small platform team relative to fleet size
    Deployment Hybrid cloud blending OpenStack with public cloud services

    Use Case: Walmart runs one of the largest OpenStack private clouds in the world, powering retail operations, supply chain, and e-commerce workloads. When they outgrew their data centres, they engineered a hybrid cloud rather than abandoning OpenStack.

    Problems:

    • Manual upgrades at hyperscale are impossible — a million cores cannot tolerate downtime windows.
    • Hardware failures at this scale are not exceptions; they are constant background noise.
    • Visibility into cloud health across such a massive fleet requires purpose-built tooling.

    Solutions:

    • Built a stateless, in-place upgrade system starting in 2018. The entire million-core fleet is upgraded annually in three months, skipping intermediate versions.
    • Developed self-healing automation at two layers: control plane automation to fix OpenStack component issues, and hardware-layer automation to detect and remove failing machines before they cause problems.
    • Created Galaxy, an internal real-time visual health-check tool that enables pinpointing and fixing issues within minutes.

    Key takeaway

    Running 1M+ cores with a small team is only possible with deep automation. Manual processes are simply not an option. — Gerald (Walmart), OpenInfra User Story

    Target — 32,000 Cores¶

    Use Case: Target started with OpenStack Icehouse and Ceph in 2015 as a development experiment. After proving the platform, they expanded to 32,000 cores with over 750,000 VMs launched across development and production, keeping approximately 13,000 VMs active at any time.

    Problem: Initial HDD-backed Ceph storage did not meet performance requirements for their growing workload diversity.

    Solution: Migrated Ceph to SSD-backed storage for both block and object, significantly improving I/O performance. Ceph is now used as the unified storage backend.

    PLATFORMA — 2,000+ VMs in Production¶

    Use Case: PLATFORMA deploys OpenStack for multiple clients as a managed cloud platform, running over 2,000 VMs in production.

    Problems:

    • Neutron is the single biggest source of complexity and failure — VLAN config, floating IP allocation, security groups, and DNS must all work perfectly for every tenant.
    • OpenStack does not fail gracefully. A Nova scheduler running out of memory silently stops scheduling. A Neutron agent that loses RabbitMQ connectivity silently stops processing.
    • Upgrade processes involve database migrations, service-by-service restarts, and API compatibility windows.

    Solutions:

    • Standardized the network topology. Every deployment uses the same VLAN layout, security group templates, and floating IP pools. Clients cannot customise network architecture — "that's where chaos lives."
    • Monitor 200+ metrics per deployment: service health, RabbitMQ queue depths, database connection pools, API response times, hypervisor utilisation, and Ceph cluster health. Every metric has an alert threshold, and every alert has a runbook.
    • Rolling upgrade process that upgrades one service at a time with automated health checks between each step. Every upgrade is first tested in a lab with production-realistic data.

    Silent failures

    Without deep monitoring, you only discover OpenStack failures when customers complain. Silence is often a sign of failure — agents may stop processing without alerting the API. — PLATFORMA Blog

    2. VMware Migration (Post-Broadcom)¶

    Broadcom's acquisition of VMware and subsequent licensing changes have triggered a mass re-evaluation of virtualisation strategies. Over 80% of OpenInfra members have received requests to migrate workloads from VMware to OpenStack, and 60% have already completed a successful migration.

    UPONU GmbH — Full VMware Exit¶

    Use Case: UPONU migrated their entire infrastructure from VMware to OpenStack, not as a cost decision but as a strategic one — control over infrastructure, development, dependencies, and no surprise licence changes.

    Problem: The migration required replacing not just a hypervisor but an entire operational philosophy — runbooks, monitoring, compliance workflows, and team skills all needed to change.

    Solution: Adopted the Sovereign Cloud Stack (SCS) reference architecture — a European open-source initiative providing standardised, validated OpenStack with certified components and defined upgrade paths. Built a parallel environment over time rather than attempting a weekend cutover. Today they operate their OpenStack platform completely autonomously.

    "We deliberately chose to use the OpenStack operations platform of the Sovereign Cloud Stack. Our decision in favour of OpenStack was not a cost decision. It was a strategic one." — UPONU Blog

    Community Consensus on Migration Timelines¶

    Migration Approach Typical Labour Multiplier
    VMware to OpenStack (commercial distribution) 1.8 - 2.5x original estimate
    VMware to Nutanix AHV 1.2 - 1.7x
    VMware to KVM (unmanaged) 2.0 - 3.0x

    Key lessons from the community:

    1. Do the operational archaeology first. Document every integration, every runbook, every team dependency — not just the ones in your architecture diagrams, the real ones that make your infrastructure work.
    2. Plan for 18-24 months minimum. Not because you're slow, but because operational transformation takes time.
    3. Accept that some workloads should stay on VMware. Some applications are so deeply integrated that the cost of unwinding exceeds the cost of staying. That's a business decision, not a technical failure.
    4. Storage migration deserves particular attention. VMware's VMFS and vSAN have different performance characteristics than Ceph. Validate performance under realistic workload conditions before committing production data.

    Migration tools available:

    • os-migrate — Ansible collection for OpenStack-to-OpenStack migrations
    • virt-v2v — Open-source disk format conversion (VMDK to QCOW2)
    • OpenInfra VMware Migration Guide — Free, vendor-neutral playbook

    Key takeaway

    The VMware migration is not a technology problem. It is an operational unwinding problem masquerading as a technology problem. — The CTO Advisor

    3. AI / GPU Factory¶

    FPT Smart Cloud — 2,000 GPUs Across Two Countries¶

    Use Case: FPT Smart Cloud built an OpenStack and NVIDIA-powered AI factory managing 1,000 H100 GPUs in Vietnam and 1,000 H200 GPUs in Japan. Workloads include eKYC bank authentication (50 GPU cards across 2 regions) and GPU-accelerated cloud desktops.

    Problem: Proprietary solutions (VMware, Azure) introduced overhead and licensing costs that scaled poorly with GPU-intensive AI workloads.

    Solutions:

    • Achieved 7% GPU efficiency improvement over VMware by using OpenStack's direct passthrough and NUMA-aware placement, translating to multi-million-dollar savings.
    • Leveraged GPU live migration (introduced in OpenStack 2024.2) to transfer running VMs with attached vGPUs between hosts without workload interruption.
    • Used Senlin autoscaling with GPU flavours for elastic scaling of eKYC workloads.

    Dawn Supercomputer — UK's Fastest AI System¶

    Use Case: The University of Cambridge, Intel, and Dell Technologies built Dawn — the UK's fastest AI supercomputer — using Scientific OpenStack developed by StackHPC. The system provides 256 Dell PowerEdge XE9640 nodes with 1,024 Intel Data Center GPU Max 1550 accelerators.

    Problem: Traditional HPC batch-only interfaces are inaccessible to researchers not versed in supercomputer systems. The system needed to serve 140+ users across 65 different AI and simulation projects with varying skill levels.

    Solution: Scientific OpenStack presents the complex supercomputer through a cloud API experience, allowing engineers and scientists to self-serve compute resources without understanding the underlying hardware complexity. The system is part of the UK AI Research Resource (AIRR), a national facility supporting research in healthcare, fusion energy, and climate modelling.

    "We've got really fast results from the machine, so for a system straight out of the blocks, it's working extremely well." — Dr. Paul Calleja, Director of Research Computing

    OpenStack for AI — Platform Capabilities¶

    The OpenInfra community has been building AI-specific capabilities into OpenStack:

    • NUMA-aware placement — Pin GPU workloads to the same NUMA node as their network and storage I/O paths
    • Multi-tenant GPU scheduling — Nova can schedule fractional GPUs (vGPU) or full passthrough GPUs per tenant
    • Ironic bare-metal provisioning — Deploy bootable container images directly to bare-metal hosts for ML training without hypervisor overhead
    • Agent-to-agent protocol support — Distributed LLM orchestration across multiple compute nodes

    See the OpenStack for AI white paper for architecture details.

    4. Telco / NFV / 5G Edge¶

    OpenStack is the de facto infrastructure layer for Network Functions Virtualisation. 84% of Communication Service Providers say OpenStack is essential or important to their company's success.

    KDDI — "Shift on Stack" for 5G Core¶

    Use Case: KDDI, one of Japan's leading telecom operators, runs OpenShift on top of OpenStack ("Shift on Stack") to host cloud-native 5G Core network functions (CNFs) defined in 3GPP Release 16+.

    Problems:

    • Virtualisation introduces overhead compared to bare metal, particularly for latency-sensitive telco workloads.
    • Short product lifecycles of CNF vendors create constant integration churn.
    • Complex networking requirements (SR-IOV, DPDK, Multus) add deployment complexity.

    Solution: Leveraged Red Hat OpenStack Platform as the IaaS foundation with OpenShift for container orchestration. The "Shift on Stack" architecture provides hardware abstraction and automation while meeting telco-grade performance requirements through SR-IOV passthrough and CPU pinning.

    BT — Charmed OpenStack for 5G Core NFVI¶

    Use Case: BT, one of Europe's largest telcos, uses Canonical's Charmed OpenStack to build NFV Infrastructure for their 5G Core deployment across hundreds of distributed edge nodes.

    Problem: Deploying and operating OpenStack in distributed environments with hundreds of nodes is extremely complex, especially with telco extensions like SDN and DPDK.

    Solution: Used Juju charms for application modelling and orchestration — deploying not just OpenStack but the entire logging, monitoring, and supporting services stack. MAAS handles bare-metal provisioning, LXD containerises control services, and charms abstract the operational complexity so the telco team can focus on VNFs rather than infrastructure plumbing.

    Edge Architecture Patterns¶

    The community has converged on architectural patterns for distributed 5G edge:

    • Hyperconverged Infrastructure (HCI) with Ceph at each edge site — compute and storage co-located on the same nodes
    • Distributed Compute Nodes (DCN) — centralised control plane managing far-edge compute nodes, reducing the number of control planes needed
    • 3-node minimum per edge site for Ceph quorum and HA
    • StarlingX for edge-specific lifecycle management in telco environments

    5. Retail and Automotive¶

    Schwarz IT / STACKIT — Lidl and Kaufland¶

    Use Case: STACKIT, the digital brand of Schwarz IT (Europe's largest retail group), runs OpenStack as the foundation for services powering nearly 13,000 Lidl and Kaufland stores plus PreZero logistics.

    Metric Value
    Compute nodes 300+ across 3 data centres
    CPU cores 7,000+
    RAM 140 TB
    Monthly data transfer 150 TB to/from OpenStack, 11 PB between data centres
    Higher-level services Hundreds of K8s clusters, 2 Cloud Foundry environments, multiple databases

    Problem: Rapid growth during the pandemic required fast scaling. Dependency on an external service provider for lifecycle management limited agility.

    Solution: Developed Yaook — an open-source OpenStack Lifecycle Management solution based on the Kubernetes Operator Pattern (Apache-2 licensed). This gave them independence from external providers and the ability to add OpenStack clusters and disaster recovery data centres on their own terms.

    Hyundai Motor Group — HCloud for Connected Cars¶

    Use Case: Hyundai built HCloud, a private cloud on OpenStack managed with Rancher, to support connected car services for 10 million+ vehicles across 4 global regions (Seoul, Los Angeles, Frankfurt, and more via Equinix).

    Problem: Rapid growth in connected car subscribers created scalability and service quality challenges. Features like remote engine start, on-demand diagnostics, remote door lock/unlock, and OTA updates require low-latency, highly available infrastructure across continents.

    Solution: Deployed HCloud in Equinix International Business Exchange data centres and interconnected to AWS via Equinix Fabric for a hybrid multicloud architecture. This provides reliable connectivity, consistent service coverage, and lower latency globally.

    "These cloud services built using Open Source have allowed us to reduce downtime and improve services to our customers. In the latest JD Power Rankings, Hyundai, Kia, and Genesis cars consistently rank in the top 5 for services in their relevant sectors." — Hyundai Motor Group

    6. Scientific Research and HPC¶

    NASA — 9,000+ Cores¶

    NASA was an early adopter of OpenStack and co-developed Nova (the compute project) alongside Rackspace. They currently run over 9,000 OpenStack cores in production, trusting open-source infrastructure for space flight simulations and research computing.

    Vienna Biocenter — HPC for 500 Scientists¶

    Use Case: The Vienna Biocenter campus (IMBA, GMI) serves 40 research groups and ~500 scientists with HPC infrastructure. A team of 14 delivers IT services from workstations to high-performance computing.

    Problem: The existing infrastructure was "a nightmare to manage" — siloed islands that couldn't communicate, with no way to automate across them.

    Solution: Built an OpenStack private cloud with Slurm workload manager that adjusts to demand. Timeline: ~2 months for proof-of-concept, ~8 months for analysis and planning, ~2 months to move into production. Runs 3 environments (dev, staging, production) to practice upgrades.

    Lesson learned

    "OpenStack is not a product. It is a framework." The out-of-box experience and scalability for certain subcomponents is "not optimal" and should be considered more like a reference implementation. — Florian Forai, Vienna Biocenter, Superuser

    INFN Cloud Area Padovana — Physics Research¶

    Use Case: The Italian National Institute for Nuclear Physics (INFN) runs an OpenStack-based IaaS for ~100 scientists across ~30 research groups, handling interactive jobs, batch and parallel applications, and development workloads. In production since 2014.

    Problem: Balancing the need for latest features/fixes against limited manpower for upgrades.

    Solution: Adopted a policy of one OpenStack upgrade per year (skipping one release). Updates are automatically tested using monitoring infrastructure before being applied to production. This strategy has kept the platform stable since 2014 with minimal staff.

    DKRZ — Climate Research¶

    The German Climate Computing Centre (DKRZ) runs a FishOS-managed OpenStack deployment specifically for climate modelling workloads, demonstrating OpenStack's applicability to large-scale environmental science simulations.

    7. Networking Deep Dives (Mailing List)¶

    DVR to OVN Migration¶

    Thread: openstack-discuss — New deployment / suggestions for network

    Problem: DVR (Distributed Virtual Router) in Neutron has unfixed bugs relating to ARP and protocols like VRRP, which Octavia Amphora load balancers rely on. This results in essentially non-functional automated failover for Amphora VIPs.

    Solution: Migrate to OVN, which handles allowed-address-pairs correctly. OVN resolves the DVR issues.

    Trade-off: OVN does not support VPNaaS and only provides Layer 4 load balancing natively. However, Octavia Amphora-based load balancers (Layer 7) can still be used with the OVN ML2 plugin — you do not need to use the OVN provider driver in Octavia.

    # Recommended: OVN as ML2 plugin + Octavia Amphora for L7 LB
neutron_plugin_agent = ovn
# Octavia still uses Amphora driver, NOT the OVN provider

    Standalone Ironic with OVN¶

    Thread: openstack-discuss — What I had to do to get standalone Ironic working with OVN

    Problem: Standalone Ironic deployments with OVN enabled experience port binding failures because the default ML2 driver does not understand bare-metal port types.

    Solution: Use the baremetal ML2 driver and ensure proper network interface configuration for Ironic nodes. This is a subtle but critical requirement that is not well-documented.

    L2 Networks Do Not Scale¶

    Source: Ceph Days NYC 2024 — Designing and Tuning for All-Flash Ceph RBD Storage

    Problem: L2 networks cause weird interoperability issues between different vendors at thousands of VMs. Debugging ARP storms, broadcast domains, and spanning tree issues in large flat L2 networks is extremely difficult.

    Solution: Switch to L3 fabrics (BGP-based spine-leaf topologies). L3 routing eliminates broadcast domains and provides deterministic, debuggable traffic paths at scale.

    8. Ceph Storage Tuning (Community Lessons)¶

    These lessons come from production Ceph deployments backing OpenStack clouds, compiled from community blogs, Ceph Days talks, and mailing list discussions.

    Linux Kernel Defaults Are Your Enemy¶

    The root cause of most Ceph performance issues is not Ceph itself but the Linux kernel, which ships defaults optimised for general-purpose workloads.

    Setting Default Recommended Why
    CPU Governor powersave / ondemand performance Prevents latency spikes during I/O bursts; benchmarks show dramatically lower IOPS with powersave
    Transparent Huge Pages always never THP + tcmalloc causes uncontrolled OSD memory growth, potentially OOM kills
    Swappiness 60 0-1 Prevents OSD stalling from paging; but do not disable swap entirely
    I/O Scheduler (NVMe) mq-deadline none NVMe devices have their own hardware queues; kernel scheduling adds overhead 
    # Apply on all Ceph nodes
echo performance | tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor
echo never > /sys/kernel/mm/transparent_hugepage/enabled
echo 0 > /proc/sys/vm/swappiness
echo none > /sys/block/nvme*/queue/scheduler

    NUMA Pinning Is Critical¶

    Cross-NUMA-socket latency is a silent performance killer, especially in all-flash deployments.

    Problem: When an OSD process runs on CPU socket 0 but its NVMe drive is attached to PCIe lanes on socket 1, every I/O operation pays a cross-socket memory access penalty. At high IOPS this becomes the dominant latency source.

    Solution: Pin OSD processes, NICs, and NVMe drives to the same NUMA node. Verify with:

    # Check NUMA node for NVMe device
cat /sys/block/nvme0n1/device/numa_node

# Check NUMA node for network interface
cat /sys/class/net/ens3f0/device/numa_node

# Pin OSD to matching NUMA node via systemd
# [Service]
# CPUAffinity=0-31  # cores on NUMA node 0

    Hidden BIOS settings

    Check your BIOS for settings that claim to "optimise" NUMA. Many server BIOSes enable interleaving or sub-NUMA clustering by default, which defeats manual NUMA pinning. Disable these unless you have specifically tested their impact.

    "Your Cluster Is Only as Fast as Your Slowest OSD"¶

    Problem: In an all-flash cluster, a single sluggish OSD drags down the entire pool's latency because clients wait for the slowest replica to acknowledge writes.

    Solutions:

    • Use time-series telemetry to detect intermittent outliers — an OSD that is slow now may be fine later, and vice versa.
    • Monitor osd_op_latency percentiles (p99, p999) not just averages.
    • Do not blindly copy ceph.conf settings from online guides. Understand why each setting exists and how it interacts with your hardware.
    • Set osd_op_thread_suicide_timeout appropriately for SSD (lower, e.g. <30s) vs HDD (higher) use cases.

    Network Tuning for Ceph¶

    Default TCP settings are optimised for web traffic, not the bursty, high-connection-count workload that Ceph generates.

    # Expand socket buffers for bursty I/O (apply on all Ceph nodes)
sysctl -w net.core.rmem_max=67108864
sysctl -w net.core.wmem_max=67108864
sysctl -w net.ipv4.tcp_rmem="4096 87380 33554432"
sysctl -w net.ipv4.tcp_wmem="4096 65536 33554432"

# Keep congestion window warm between bursts
sysctl -w net.ipv4.tcp_slow_start_after_idle=0

# Wide ephemeral port range for high connection counts
sysctl -w net.ipv4.ip_local_port_range="1024 65535"

# Deep connection queue for spike handling
sysctl -w net.core.somaxconn=65535

# Enable jumbo frames on Ceph cluster network (MTU 9000)
ip link set dev ens3f0 mtu 9000

    Test before and after

    Always benchmark with fio or ceph tell osd.* bench before and after applying tunings to confirm actual gains. Default settings are rarely optimal for production scale, but changes should be validated against your specific hardware and workload mix. — Brett Petch

    Upgrade Lessons from the Trenches¶

    A bonus section on the universal challenge of OpenStack upgrades:

    Kolla-Ansible SLURP Upgrade (2024.1 to 2025.1)¶

    Source: Rok's Blog — Lessons from the Trenches

    Lessons learned:

    1. Always update within the same release first — update to the latest Kolla-Ansible patch release for your current version before attempting a major upgrade.
    2. Never trust backups without restore tests — untested backups are not backups.
    3. RabbitMQ changes are more disruptive than they look — queue durability changes require careful handling; API calls will fail during the queue reset window.
    4. Running workloads survive — VMs connected via SSH had no disconnects during the upgrade. The data plane is isolated from control plane disruption.
    5. Test Magnum after upgrade — if you use Container-as-a-Service, validate CAPI integration post-upgrade as it is a common regression point.

    OpenStack-as-a-Service with Krateo¶

    Source: Diego Braga — OpenStack-as-a-Service with Krateo (June 2026)

    A novel approach: package the entire OpenStack-Helm stack as Krateo PlatformOps blueprints so that a single kubectl apply rolls out a working OpenStack. Key bugs discovered:

    • Helm hook annotations appear in two forms (helm.sh/hook: and "helm.sh/hook":) — missing the quoted form deadlocked Keystone's fernet-setup.
    • OpenStack-Helm's configmap-etc generates a random memcache_secret_key on each render, causing rolling restarts on every reconcile. Fix: pin the key in values.

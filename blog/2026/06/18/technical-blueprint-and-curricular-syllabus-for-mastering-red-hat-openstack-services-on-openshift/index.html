    Technical Blueprint and Curricular Syllabus for Mastering Red Hat OpenStack Services on OpenShift¶

    Red Hat OpenStack Services on OpenShift (RHOSO) represents a fundamental shift in how enterprise Infrastructure-as-a-Service (IaaS) is designed, deployed, and managed. By migrating the traditional OpenStack control plane from legacy TripleO-directed bare-metal deployments into a podified, container-native architecture hosted on Red Hat OpenShift Container Platform (RHOCP), RHOSO delivers an efficient, declarative control plane while maintaining a highly performant, distributed data plane on bare-metal Red Hat Enterprise Linux (RHEL) nodes.

    This paradigm shift requires platform administrators and systems engineers to develop new technical competencies. Mastering RHOSO demands proficiency across three foundational pillars—Compute, Networking, and Storage—alongside structured learning paths and advanced operational troubleshooting methodologies.

    Architectural Taxonomy of RHOSO¶

    In a container-native environment, the administrative control plane is decoupled from the user-workload data plane. The control plane components execute as Kubernetes-native workloads managed by custom operators inside the RHOCP cluster, whereas the data plane consists of external bare-metal RHEL hosts managed via the External Data Plane Management (EDPM) automation engine.

    Technical Mastery Domain 1: Compute Infrastructure¶

    The compute tier in RHOSO shifts virtualization management from manual host-level scripting to a declarative framework driven by Kubernetes Custom Resource Definitions (CRDs). The platform uses the EDPM engine to execute containerized Ansible runners, enabling parallelized operations and establishing robust micro-failure domains across compute node sets.

    Key Compute Core Concepts¶

    To master compute orchestration within a podified cloud ecosystem, architects must gain competency in several core areas:

    Declarative Machine Ingestion: Deploying compute nodes via declarative CRDs. This involves using the Bare Metal Operator (BMO) and configuring BareMetalHost and OpenStackDataPlaneNodeSet resources to automate OS installations and platform registration.

    Image-Based Deployments: Preparing, customizing, and scaling target infrastructure nodes using containerized bootc (Image Mode) operating system images.

    High Availability and Evacuation: Standardizing failure recovery using Instance High Availability (Instance HA) to automate the evacuation and recreation of virtual machines on healthy hosts when a physical compute failure is detected.

    Distributed Edge Topologies: Implementing Distributed Compute Nodes (DCN) backed by local Red Hat Ceph Storage endpoints to support low-latency requirements.

    Database and MQ Cell Architectures: Configuring and validating multi-cell environments to isolate database transactions and message queues, which mitigates scalability bottlenecks in large installations.

    Technical Mastery Domain 2: Advanced Networking and Software-Defined Infrastructures¶

    In RHOSO, networking transitions from legacy Neutron agents on bare-metal to an orchestrator-managed hierarchy. This design integrates the Kubernetes NMState operator for node network policies, Multus for multi-interface pods, and OVN-Kubernetes as the core SDN engine.

    Key Networking Core Concepts¶

    Mastering this network virtualization topology requires addressing several integration challenges:

    Host Network State Management: Writing declarative states via NMState to control interface bonds, VLAN interfaces, and MTU settings across OpenShift and data plane nodes.

    Virtual IP Allocation and Announcement: Managing MetalLB configuration pools and Layer 2 or BGP announcements to ensure high availability for API service VIPs.

    Dynamic Spine-Leaf Routing: Deploying dynamic routing on the data plane using Free Range Routing (FRR) and BGP, which requires Distributed Virtual Routing (DVR) to scale external traffic routing.

    Load Balancing Resiliency: Configuring dynamic flow resumption in Octavia to automatically reassign active load-balancing tasks to surviving controllers during an outage.

    Automated DNS Infrastructures: Deploying and managing Designate to provide multitenant, automated DNS-as-a-Service, integrated with the control plane's DNSmasq hierarchy and upstream enterprise DNS resolvers.

    Technical Mastery Domain 3: Storage Integration¶

    The RHOSO storage framework manages two distinct storage pathways: persistent storage for control plane service states (e.g., databases) using Container Storage Interface (CSI) drivers, and scalable backends for virtual machines on the data plane.

    Key Storage Core Concepts¶

    Mastering storage integration requires an understanding of persistent storage architectures:

    Control Plane CSI Orchestration: Managing high-performance CSI storage engines like Portworx to handle persistent volumes for database and caching pods.

    External Ceph Integration: Connecting Glance (image), Cinder (block), and Manila (file) services to external Red Hat Ceph Storage clusters.

    Distributed Object Storage: Deploying Swift on external data plane nodes to improve horizontal scalability and performance for large object repositories.

    Enterprise Multi-Backend Configuration: Integrating specialized drivers like the Pure Storage FlashArray volume driver or Dell PowerFlex SDC (Storage Data Client) to support multi-backend Cinder configurations.

    Storage Bus Notifications: Enabling event notifications in Cinder and Manila by configuring notificationsBusInstance to output metrics to a RabbitMQ bus.

    Operational Troubleshooting and Diagnostic Blueprint¶

    Diagnosing issues in a container-native, operator-driven control plane requires a structured troubleshooting methodology. Because failures can occur across container runtimes, Kubernetes operators, physical host nodes, or network configurations, administrators must systematically check components to identify the root cause.

    1. Control Plane & Operator Diagnostics¶

    When debugging control plane operators, administrators should first verify the overall health of the OpenShift operators and core cluster resources.

    Operator Health Assessment: Run commands to check that the core operators are responding and healthy:

    oc get co
oc get clusterversion

    Pod Timeline Audit: Review the timeline of events within the openstack namespace to identify crashes, rescheduling loops, or provisioning delays:

    oc get events -n openstack --sort-by=.lastTimestamp

    Resource Pressure Evaluation: Check for memory or CPU contention on the host OpenShift nodes, which can cause pod eviction or database replication timeouts:

    oc describe nodes | grep -E "CPU|Memory|Disk"
kubectl top node

    2. Namespace Webhooks & Validation Constraints¶

    A common issue during installation or upgrade is when custom resources fail to reconcile because API webhooks are blocked.

    Namespace Validation: Verify that the target namespace is configured to allow privileged pod creation. If the Security Context Constraint (SCC) is set incorrectly, webhook execution will fail and prevent resource instantiation:

    oc get namespace openstack -o jsonpath='{.metadata.labels}'

    Namespace Label Configuration: Ensure the appropriate security context flags are applied to the namespace:

    oc label ns openstack security.openshift.io/scc.podSecurityLabelSync=false --overwrite
oc label ns openstack pod-security.kubernetes.io/enforce=privileged --overwrite

    Custom Resource Name Verification: Ensure that custom resource definitions do not exceed the 63-character limit. Long names can trigger silent webhook validation errors or cause truncation issues during deployment.

    3. NMState & Network Infrastructure Diagnostics¶

    If host-level physical configurations are misconfigured, network isolation or interface routing can fail.

    Network Policy Failures: When a NodeNetworkConfigurationPolicy (NNCP) fails to apply, check the generated NodeNetworkConfigurationEnactment (NNCE) objects for the target node to locate the configuration error:

    oc get nnce -o yaml

    Handler Log Extraction: Extract logs directly from the NMState handler daemon running on the failing physical host:

    oc logs -n openshift-nmstate -l app=kubernetes-nmstate-handler --tail=100

    ARP and Speaker Alignment Check: If MetalLB is failing to announce virtual VIP addresses, check if the Speaker pods are running on nodes that lack the physical OpenStack interfaces, which will prevent them from answering ARP queries.

    4. EDPM & Data Plane Diagnostics¶

    If a compute or networker node set fails to deploy or scale, administrators can use several diagnostics to isolate the issue.

    Job Condition Verification: Inspect the validation status and message history of the failed job object within the targeted node set:

    oc describe openstackdataplanenodeset <nodeset_name> -n openstack

    Ansible Runner Log Analysis: Because EDPM runs via containerized Ansible environments, review the log stream of the active runner pod to identify the step where the execution failed:

    oc logs -n openstack jobs/openstack-ansible-runner-<task-suffix>

    Data Plane Target Verification: Check the SSH authorization configurations and verify that the target bare-metal hosts contain the private keys specified in the corresponding credential secret:

    oc get secret dataplane-adoption-secret -n openstack -o jsonpath='{.data.ssh-privatekey}' | base64 -d

    Comprehensive Data Gathering: Avoid generic OpenShift debugging commands. Instead, run the specialized OpenStack utility to capture full configuration states and logs across both the control and data planes:

    oc adm must-gather --image=registry.redhat.io/rhoso/openstack-must-gather-rhel9:latest

    Summary¶

    RHOSO demands a cross-domain skill set spanning Kubernetes operators, declarative CRDs, bare-metal automation, and traditional OpenStack service expertise. The three mastery domains—Compute, Networking, and Storage—each have distinct architectural patterns but share a common operational model: define intent in YAML, reconcile via operators, and troubleshoot across both the podified control plane and the EDPM-managed data plane.

    Use the structured curricula above as a progressive learning path: establish Linux and Ansible foundations, deepen OpenShift and OpenStack administration skills through official training, then specialize using the RHOSO 18.0 documentation for deployment customization, scale planning, and partner integrations.

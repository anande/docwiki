    Production ML Reference Architecture — KServe, vLLM & Kubeflow on OpenShift/OpenStack¶

    Planning infrastructure for a production-grade ML serving stack is non-trivial. This post is a reference architecture covering hardware sizing, GPU compute (including MIG), network design, storage tiers, and performance tuning for maximum inference throughput.

    Component Specification Quantity
    CPU 2× Intel Xeon Gold 6348 (28C) or AMD EPYC 7543 (32C) 3 nodes (HA)
    RAM 256 GB DDR4 ECC per node
    Storage (OS) 2× 480GB SSD (RAID 1) per node
    Storage (Ceph OSD) 4× 3.84TB NVMe SSD per node (converged)

    OpenShift Control Plane¶

    Component Specification Quantity

    RAM 32 GB per node

    CPU Workers (Pipelines, Notebooks, Preprocessing)¶

    Component Specification Quantity
    vCPU 32–64 vCPUs 3–6 nodes
    RAM 128–256 GB per node
    Storage 1TB NVMe (ephemeral) per node

    GPU Workers (Training + Inference)¶

    Component Specification Quantity
    CPU 2× AMD EPYC 9454 (48C) or Intel Xeon w9-3495X per node
    RAM 512 GB – 1 TB DDR5 ECC per node
    GPU 4× or 8× NVIDIA H100 80GB SXM5 per node
    GPU Interconnect NVLink 4.0 (900 GB/s) + NVSwitch intra-node
    Storage 2× 3.84TB NVMe Gen4 (model cache) per node
    Network (Data) 2× 100GbE (bonded) or 1× 400GbE per node
    Network (GPU) InfiniBand NDR 400Gb/s or RoCEv2 per node
    Power ~10kW per 8-GPU node per node

    NVIDIA Multi-Instance GPU (MIG) for Inference¶

    MIG allows a single physical GPU to be partitioned into isolated instances, each with dedicated compute, memory, and cache resources. This is transformative for multi-tenant inference.

    Why MIG for Production Inference¶

    • Hardware isolation — each MIG instance has dedicated SM (Streaming Multiprocessor) slices, memory bandwidth, and L2 cache
    • QoS guarantees — noisy neighbor problem eliminated; one model can't starve another
    • Cost efficiency — serve multiple small models on one H100 instead of dedicating an entire 80GB GPU to a 7B model using 14GB
    • Fault isolation — an OOM in one instance doesn't crash others

    MIG Profiles (H100 80GB)¶

    Profile Memory Compute (SMs) Use Case
    1g.10gb 10 GB 1/7 (16 SMs) 7B INT4/INT8 quantized models
    2g.20gb 20 GB 2/7 (32 SMs) 7B FP16, small embedding models
    3g.40gb 40 GB 3/7 (48 SMs) 13B FP16 or 70B AWQ/GPTQ
    4g.40gb 40 GB 4/7 (64 SMs) 13B with large batch sizes
    7g.80gb 80 GB 7/7 (132 SMs) 70B FP16, full GPU for one model

    MIG Configuration on OpenShift¶

    apiVersion: nvidia.com/v1
kind: ClusterPolicy
metadata:
  name: gpu-cluster-policy
spec:
  operator:
    defaultRuntime: crio
  driver:
    enabled: true
  devicePlugin:
    enabled: true
  migManager:
    enabled: true
    config:
      name: mig-config
  dcgmExporter:
    enabled: true
  gfd:
    enabled: true
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: mig-config
  namespace: nvidia-gpu-operator
data:
  config.yaml: |
    version: v1
    mig-configs:
      # Inference-optimized: 2× large + 4× small instances per GPU
      inference-mixed:
        - devices: [0, 1]
          mig-enabled: true
          mig-devices:
            "3g.40gb": 2    # Two 40GB slices → 13B models each
        - devices: [2, 3]
          mig-enabled: true
          mig-devices:
            "1g.10gb": 7    # Seven 10GB slices → 7B quantized models
        - devices: [4, 5, 6, 7]
          mig-enabled: false  # Full GPUs for TP across 4 GPUs (70B model)

      # Training: all GPUs full (no MIG)
      training-full:
        - devices: all
          mig-enabled: false

      # Multi-tenant small models
      multi-tenant-small:
        - devices: all
          mig-enabled: true
          mig-devices:
            "2g.20gb": 3    # Three 20GB slices per GPU = 24 instances on 8 GPUs

    MIG Scheduling Strategy¶

    8× H100 SXM5 node — mixed MIG configuration:
┌─────────────────────────────────────────────────────────────────┐
│ GPU 0-1: MIG 3g.40gb × 2 each = 4 instances                    │
│   → 4× 13B model replicas (one per MIG instance)               │
│                                                                  │
│ GPU 2-3: MIG 1g.10gb × 7 each = 14 instances                   │
│   → 14× 7B-INT4 model replicas (embeddings, classifiers, etc.) │
│                                                                  │
│ GPU 4-7: Full GPUs, tensor-parallel group                       │
│   → 1× 70B model with TP=4                                     │
└─────────────────────────────────────────────────────────────────┘
Total on single node: 1× 70B + 4× 13B + 14× 7B = 19 model instances

    Network Performance Tuning¶

    Enable Jumbo Frames on Storage and GPU Networks¶

    # On each GPU/storage node (via MachineConfig on OpenShift)
ip link set eth1 mtu 9000    # Storage interface
ip link set eth2 mtu 9000    # GPU fabric interface

    # OpenShift MachineConfig for jumbo frames
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfig
metadata:
  name: 99-gpu-worker-jumbo-frames
  labels:
    machineconfiguration.openshift.io/role: gpu-worker
spec:
  config:
    ignition:
      version: 3.2.0
    storage:
      files:
        - path: /etc/NetworkManager/dispatcher.d/99-jumbo-frames.sh
          mode: 0755
          contents:
            inline: |
              #!/bin/bash
              if [[ "$1" == "eth1" || "$1" == "eth2" ]]; then
                ip link set "$1" mtu 9000
              fi

    NCCL Tuning for Multi-GPU Communication¶

    env:
  # Use InfiniBand for NCCL (multi-node training)
  - name: NCCL_IB_DISABLE
    value: "0"
  - name: NCCL_IB_HCA
    value: "mlx5_0,mlx5_1,mlx5_2,mlx5_3"
  - name: NCCL_IB_GID_INDEX
    value: "3"
  # Use NVLink for intra-node (tensor parallelism)
  - name: NCCL_P2P_LEVEL
    value: "NVL"           # Force NVLink for peer-to-peer
  - name: NCCL_NET_GDR_LEVEL
    value: "PIX"           # GPU Direct RDMA level
  # Buffering and threading
  - name: NCCL_BUFFSIZE
    value: "8388608"       # 8MB buffers (default 4MB)
  - name: NCCL_NTHREADS
    value: "512"           # Max threads per NCCL operation
  - name: NCCL_SOCKET_IFNAME
    value: "eth2"          # GPU fabric interface
  # Topology detection
  - name: NCCL_TOPO_DUMP_FILE
    value: "/tmp/nccl_topo.xml"

    RoCEv2 Lossless Ethernet Configuration¶

    If using RoCEv2 instead of InfiniBand:

    # Enable Priority Flow Control (PFC) on switch ports
# (switch-specific — example for Mellanox/NVIDIA Spectrum)
interface ethernet 1/1-1/32
  dcb priority-flow-control mode on
  dcb priority-flow-control priority 3 enable
  dcb ets traffic-class 3 bandwidth 80

# Enable ECN on the host
sysctl -w net.ipv4.tcp_ecn=1
mlnx_qos -i eth2 --pfc 0,0,0,1,0,0,0,0    # PFC on priority 3
cma_roce_tos -d mlx5_0 -t 106               # DSCP for RoCE traffic

    Service Mesh Bypass for Hot Inference Path¶

    apiVersion: networking.istio.io/v1beta1

metadata:
  name: vllm-bypass-mtls
  namespace: model-serving
spec:
  selector:
    matchLabels:
      app: vllm-inference

    mode: PERMISSIVE    # Don't enforce mTLS on GPU-to-GPU inference path

    - port:
        number: 8000
        protocol: HTTP
      defaultEndpoint: 127.0.0.1:8000
  outboundTrafficPolicy:
    mode: ALLOW_ANY

    Storage Architecture & Tuning¶

    Storage Tiers¶

    Tier Backend Use Case Throughput Latency
    Hot Local NVMe (node-local) Model weight cache, active inference 6–7 GB/s <100μs
    Warm CephFS on NVMe (Manila) Shared model store, training checkpoints 3–10 GB/s 1–5ms
    Cold Ceph RGW / Swift (S3) Datasets, archived models, pipeline artifacts 1–3 GB/s 5–50ms

    Model Loading Strategy¶

    Models are large (7B = 14GB, 70B = 140GB FP16). Loading speed directly impacts pod startup time and autoscaler responsiveness.

    ┌──────────────────────────────────────────────────────────────┐
│  Model Loading Pipeline                                       │
│                                                               │
│  S3 (source of truth)  ──→  CephFS (shared warm cache)       │
│         │                          │                          │
│         │  (first pull)            │  (fast local cache)      │
│         ▼                          ▼                          │
│  ┌─────────────┐          ┌─────────────────────┐            │
│  │  Init Container│        │  hostPath NVMe       │            │
│  │  (model pull)  │──────→│  /mnt/model-cache    │            │
│  └─────────────┘          └──────────┬──────────┘            │
│                                       │                       │
│                                       ▼                       │
│                            ┌─────────────────────┐            │
│                            │  vLLM loads from     │            │
│                            │  local NVMe (6GB/s)  │            │
│                            └─────────────────────┘            │
└──────────────────────────────────────────────────────────────┘
    Storage Path Load Time (140GB model)
    S3 over 25GbE ~56 seconds
    CephFS over 100GbE ~14 seconds
    Local NVMe (pre-cached) ~20 seconds

    Compute Performance Tuning¶

    vLLM Engine Arguments for Maximum Throughput¶

    vllm serve meta-llama/Llama-3.1-70B-Instruct-AWQ \
  --tensor-parallel-size 4 \
  --dtype float16 \
  --quantization awq \
  --max-model-len 8192 \
  --max-num-seqs 256 \
  --max-num-batched-tokens 65536 \
  --gpu-memory-utilization 0.93 \
  --enable-chunked-prefill \
  --max-num-partial-prefills 4 \
  --enable-prefix-caching \
  --swap-space 32 \
  --block-size 32 \
  --num-scheduler-steps 8 \
  --use-v2-block-manager \
  --disable-log-requests
    Parameter Effect Tuning Guidance
    --gpu-memory-utilization Fraction of VRAM for KV cache 0.90–0.95 (leave headroom for activations)
    --max-num-seqs Max concurrent sequences Higher = more throughput, more memory
    --max-num-batched-tokens Tokens per iteration Limited by GPU compute; 32K–65K for H100
    --enable-chunked-prefill Interleave prefill with decode Reduces latency spikes for decode users
    --enable-prefix-caching Cache common prefixes (system prompts) Massive speedup for chat applications
    --block-size Tokens per KV cache block 16 (default) or 32 (less block table overhead)
    --swap-space GB of CPU memory for swapped KV Safety net for burst traffic
    --num-scheduler-steps Multi-step scheduling Reduces scheduling overhead

    CPU and OS-Level Tuning¶

    # OpenShift Performance Profile for GPU nodes
apiVersion: performance.openshift.io/v2
kind: PerformanceProfile
metadata:
  name: gpu-worker-performance
spec:
  cpu:
    isolated: "4-95"          # Reserve cores 4-95 for workloads
    reserved: "0-3"           # Cores 0-3 for OS/kubelet
  hugepages:
    defaultHugepagesSize: 1G
    pages:
      - size: 1G
        count: 64             # 64GB hugepages for VRAM-mapped ops
  machineConfigPoolSelector:
    matchLabels:
      machineconfiguration.openshift.io/role: gpu-worker
  nodeSelector:
    node-role.kubernetes.io/gpu-worker: ""
  realTimeKernel:
    enabled: false
  numa:
    topologyPolicy: single-numa-node    # Pin GPU pods to single NUMA
  net:
    userLevelNetworking: true           # SR-IOV / DPDK capable

    NUMA-Aware GPU Scheduling¶

    GPUs are physically connected to specific CPU NUMA nodes. Cross-NUMA access adds latency:

    # Topology Manager configuration (kubelet)
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: gpu-topology-aware
spec:
  machineConfigPoolSelector:
    matchLabels:
      machineconfiguration.openshift.io/role: gpu-worker
  kubeletConfig:
    topologyManagerPolicy: single-numa-node
    topologyManagerScope: pod
    cpuManagerPolicy: static
    reservedSystemCPUs: "0-3"
    memoryManagerPolicy: Static
    evictionHard:
      memory.available: "2Gi"

    Autoscaling for Throughput¶

    Custom Metrics HPA (vLLM-Aware)¶

    apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: llama-70b-throughput-hpa
  namespace: model-serving
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: llama-70b-predictor
  minReplicas: 2
  maxReplicas: 8
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60
      policies:
        - type: Pods
          value: 1
          periodSeconds: 120    # GPU pods take 2-3 min to start
    scaleDown:
      stabilizationWindowSeconds: 600
      policies:
        - type: Pods
          value: 1
          periodSeconds: 300
  metrics:
    - type: Pods
      pods:
        metric:
          name: vllm_num_requests_waiting
        target:
          type: AverageValue
          averageValue: "10"     # Scale up when queue depth > 10
    - type: Pods
      pods:
        metric:
          name: vllm_gpu_cache_usage_perc
        target:
          type: AverageValue
          averageValue: "80"    # Scale up when KV cache > 80% full

    Key Throughput Metrics¶

    Metric Target Alert If
    vllm_avg_generation_throughput_toks_per_s >2000 tok/s per pod (70B) <1500 tok/s sustained

    DCGM_FI_DEV_POWER_USAGE <TDP At TDP limit (clock throttle)

    Prometheus Alerting Rules¶

    apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: vllm-performance-alerts
  namespace: model-serving
spec:
  groups:
    - name: vllm-throughput
      rules:
        - alert: VLLMHighQueueDepth
          expr: avg(vllm_num_requests_waiting) > 20
          for: 2m
          labels:
            severity: warning
          annotations:
            summary: "vLLM request queue backing up"
            description: "Average queue depth {{ $value }} — consider scaling up"

        - alert: VLLMKVCacheSaturation
          expr: avg(vllm_gpu_cache_usage_perc) > 90
          for: 1m
          labels:
            severity: critical
          annotations:
            summary: "KV cache near saturation — requests will be preempted"

        - alert: GPUThermalThrottle
          expr: DCGM_FI_DEV_GPU_TEMP > 83
          for: 30s
          labels:
            severity: critical
          annotations:
            summary: "GPU {{ $labels.gpu }} at {{ $value }}°C — throttling"

    Sizing by Deployment Scale¶

    Small (POC — 5–10 users)¶

    Resource Specification
    GPU nodes 1–2 nodes, 4× A100 80GB each
    MIG usage Not needed (few models)
    Storage 30TB Ceph
    Network 25GbE all paths
    Total GPUs 4–8

    Medium (Team — 20–50 users, multiple models)¶

    Resource Specification
    GPU nodes 4–8 nodes, 4–8× H100 each
    MIG usage 2 nodes MIG-partitioned for small models
    Storage 100TB Ceph + local NVMe cache
    Network 100GbE storage, InfiniBand for training
    Total GPUs 16–64

    Large (Enterprise — 100+ users, dozens of models)¶

    Resource Specification
    GPU nodes 10–30+ nodes, 8× H100 each
    MIG usage Dedicated MIG tier for multi-tenant serving
    Storage 500TB+ Ceph + distributed NVMe cache
    Network 400GbE + InfiniBand NDR fat-tree
    Total GPUs 80–240+

    Performance Tuning Checklist¶

    Compute¶

    • Lock GPU clocks to max (nvidia-smi -ac)
    • Enable persistence mode (nvidia-smi -pm 1)
    • Use single-numa-node topology policy
    • Pin CPU cores with cpuManagerPolicy: static
    • Allocate hugepages (1G pages)
    • Set gpu-memory-utilization to 0.90–0.95
    • Enable chunked prefill and prefix caching
    • Use quantization (AWQ/FP8) where latency allows
    • Configure MIG for multi-model nodes

    Network¶

    • Jumbo frames (MTU 9000) on storage and GPU networks
    • NCCL tuned for NVLink intra-node, IB/RoCE inter-node
    • PFC + ECN enabled for RoCEv2 lossless Ethernet
    • Istio mTLS bypassed or set to PERMISSIVE for inference hot path
    • Dedicated VLAN for GPU fabric traffic
    • GPU Direct RDMA enabled (NCCL_NET_GDR_LEVEL)

    Storage¶

    • Two-tier model loading (S3 → local NVMe cache)
    • CephFS with NVMe OSDs for shared model store
    • noatime + nodiratime mount options
    • Large readahead (rbd_readahead_max_bytes = 4M)
    • Separate Ceph pools for model data vs. pipeline artifacts
    • reclaimPolicy: Retain on model StorageClasses

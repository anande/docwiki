    vLLM Architecture Deep Dive — From KV Cache Bottleneck to Production Inference¶

    Stepping into the production side of large language model deployment is an exciting milestone. To understand why vLLM (Versatile LLM) has become the gold standard for open-source model serving, we first need to examine the massive bottleneck it was built to solve: GPU memory. Every autoregressive generation step stores intermediate attention state in a KV cache — and how that cache is allocated determines whether your GPU serves ten concurrent users or a hundred.

    The Core Bottleneck: The KV Cache Problem¶

    When a model generates text, it acts autoregressively — it predicts the next token based on all previous tokens. To avoid recomputing the mathematical context of past tokens at every single step, the system stores their Keys and Values in GPU memory. This is called the KV cache.

    In traditional serving frameworks (like Hugging Face Transformers), memory for this KV cache had to be allocated contiguously and statically based on the maximum possible output length (e.g., 2048 or 4096 tokens).

    The Problem with Traditional Allocation¶

    • Internal fragmentation: If a user only requests a 10-token answer but the system reserved space for 2048 tokens, the remaining 2038 slots sit completely empty and locked up.
    • External fragmentation: Memory gets broken into tiny scattered gaps that can't be reused for new requests.
    • Because of this, up to 60% to 80% of a GPU's VRAM used to be entirely wasted, severely limiting how many concurrent users a server could handle.

    The real cost of wasted VRAM

    Naive pre-allocation reserves max_len tokens per sequence regardless of actual output length. With PagedAttention, memory waste drops below 4%, enabling 2–4× more concurrent sequences on the same hardware.

    The Two Pillars of vLLM Architecture¶

    vLLM addresses the KV cache problem through two tightly coupled innovations:

    1. PagedAttention¶

    Inspired by how operating systems use virtual memory and paging to manage RAM, vLLM treats GPU VRAM as a pool of individual, fixed-size blocks (typically 16 tokens per block). A block table keeps track of which logical sequence tokens map to which physical memory blocks — non-contiguous, dynamically allocated, with copy-on-write support for parallel sampling.

    2. Continuous Batching (Iteration-Level Scheduling)¶

    Traditional batching forces the server to wait until every single request in a batch is completely finished. vLLM uses continuous batching at the iteration level (token-by-token). As soon as a single request completes, its memory is instantly freed, and a new request jumps into the active batch on the very next cycle.

    Core Components in Detail¶

    Scheduler — The Brain¶

    The scheduler decides which requests get processed in each iteration and in what order. It implements:

    • Continuous batching — doesn't wait for an entire batch to finish before admitting new requests
    • Preemption policies — when GPU memory is exhausted, it can swap KV cache blocks to CPU or recompute them later
    • Priority queues — manages waiting, running, and swapped request queues

    Each scheduling iteration produces a SchedulerOutput containing prefill and decode assignments for the current batch — often a mixed batch of sequences at different lifecycle stages.

    Block Manager — PagedAttention's Memory Layer¶

    The block manager implements a paging system inspired by OS virtual memory:

    Concept OS Analogy vLLM Implementation
    Page 4 KB memory page KV cache block (e.g., 16 tokens worth of K and V tensors)
    Page table Virtual → physical mapping Block table mapping logical block index → physical GPU block
    Swap space Disk swap CPU memory for evicted blocks

    Key properties:

    • Non-contiguous memory — blocks can live anywhere in the physical pool
    • Copy-on-write — enables efficient parallel sampling (multiple outputs from one prompt)
    • Dynamic allocation — blocks are allocated only as tokens are generated

    Model Executor & Workers¶

    • One Worker per GPU (for tensor parallelism)
    • Each worker holds a shard of the model weights
    • Workers execute the forward pass in lockstep using NCCL for all-reduce operations

    Attention Backend¶

    vLLM selects optimized kernels depending on the phase:

    Phase Kernel Why
    Prefill FlashAttention Parallel processing of long prompts
    Decode PagedAttention Scattered KV blocks via block table lookup
    Alternative FlashInfer Drop-in backend for certain hardware/configs

    The Full Inference Pipeline¶

    Here is the complete path from request arrival to streamed response:

    API->>Engine: Create SequenceGroup

    Engine->>Sched: Enqueue sequence

    loop Decode (token-by-token)
        Sched->>GPU: Decode batch (mixed prefill + decode)

        API-->>Client: SSE chunk
    end
    Sched->>BM: Release blocks
    API-->>Client: [DONE]

    Step 1: Request Arrival¶

    The API server (FastAPI) receives an HTTP request and creates a SequenceGroup — the unit of work that tracks one or more related generation sequences (e.g., n=3 parallel samples).

    Step 2: Tokenization¶

    The input text is tokenized into token IDs. For chat models, the prompt is formatted according to the model's chat template before tokenization.

    Step 3: Scheduling Decision¶

    The scheduler checks available blocks in the block manager. If memory permits, the sequence is admitted to the running queue. The scheduler produces a SchedulerOutput with prefill and/or decode assignments for this iteration.

    Step 4: Prefill Phase¶

    All prompt tokens are processed in parallel in a single (or chunked) forward pass. Attention computes K and V tensors for every prompt token, which are stored in newly allocated KV cache blocks. This is the most compute-intensive phase for long prompts.

    Chunked prefill

    For very long prompts, vLLM can split prefill into chunks and interleave them with ongoing decode work — reducing latency spikes for other requests in the batch.

    Step 5: Decode Phase¶

    Generation proceeds token by token. Each iteration:

    1. The PagedAttention kernel reads scattered KV blocks via the block table
    2. The model computes logits for the next token
    3. A new K/V pair is appended (allocating a new block when the current 16-token block fills)

    Step 6: Continuous Batching¶

    On every iteration, the scheduler assembles a fresh batch. Completed sequences drop out immediately; new sequences (prefill) or continuing sequences (decode) take their place. A single batch may contain:

    • Sequences in prefill (processing prompts)
    • Sequences in decode (generating one token each)

    This is what makes GPU utilization stay high under variable load.

    Step 7: Sampling¶

    Raw logits pass through the sampling pipeline:

    logits → temperature scaling → top-p (nucleus) → top-k → softmax → sample

    The chosen token ID becomes the next input for the decode loop.

    Step 8: Stopping Conditions¶

    Generation stops when any of these conditions is met:

    • EOS token — end-of-sequence marker emitted by the model
    • max_tokens — user-specified output limit reached
    • Stop sequences — custom strings configured by the caller

    Step 9: Detokenization & Streaming¶

    Token IDs are converted back to text. Partial results are streamed to the client via Server-Sent Events (SSE), giving users low time-to-first-token and incremental output.

    Step 10: Completion and Cleanup¶

    When a sequence finishes, its KV cache blocks are returned to the free pool and immediately available for new requests — the core benefit of dynamic, non-contiguous allocation.

    PagedAttention: Memory Before and After¶

    Without PagedAttention (naive allocation):

    • Pre-allocate max_len for each sequence regardless of actual length
    • 60–80% of KV cache memory wasted
    • Severe fragmentation limits concurrency

    With PagedAttention:

    • Blocks scattered in physical memory; block table maps logical → physical
    • Memory waste drops to < 4%
    • 2–4× more concurrent sequences on the same GPU

    Traditional vs. vLLM Serving¶

    Feature Traditional Serving vLLM Serving
    KV cache allocation Statically allocated, continuous chunks Dynamically allocated, non-contiguous pages
    VRAM utilization Low (~20–40% used effectively) High (~96%+ used effectively)
    Batching style Static / dynamic (request-level) Continuous (iteration / token-level)
    Scalability Struggles heavily under high concurrency Scales horizontally across multiple GPUs smoothly
    Memory fragmentation High (internal + external) Minimal (< 4% waste)
    Latency under load Queues grow; GPU sits idle between batches Mixed prefill/decode keeps GPU busy

    Multi-GPU: Tensor Parallelism¶

    When a model exceeds single-GPU memory, vLLM splits weights across devices using tensor parallelism:

    • Model weights are split column-wise across GPUs
    • Each GPU holds a shard of both model weights and KV cache blocks
    • After attention and FFN layers, NCCL all-reduce synchronizes partial results
    • One Worker per GPU executes forward passes in lockstep
    vllm serve meta-llama/Llama-3.1-70B-Instruct \
  --tensor-parallel-size 4 \
  --dtype auto \
  --gpu-memory-utilization 0.9

    This is distinct from pipeline parallelism (layer splitting) and data parallelism (replicated weights, sharded batches) — vLLM's primary multi-GPU strategy for large models is tensor parallelism.

    Advanced Performance Techniques¶

    Beyond PagedAttention and continuous batching, vLLM implements a suite of optimizations for production workloads:

    Technique What it solves
    PagedAttention Memory fragmentation → more concurrent sequences
    Continuous batching GPU idle time → higher throughput
    FlashAttention (prefill) Slow attention on long prompts
    Chunked prefill Latency spikes when long prompts monopolize the GPU
    Tensor parallelism Model doesn't fit on one GPU
    Quantization (AWQ / GPTQ / FP8) Reduce memory footprint + increase throughput
    Speculative decoding Decode latency — a small draft model predicts ahead, verified by the main model
    Prefix caching Redundant prefill for shared system prompts across requests

    Speculative decoding in brief

    A lightweight draft model generates several candidate tokens ahead of time. The main model verifies them in a single forward pass. Accepted tokens skip individual decode iterations, reducing latency for memory-bandwidth-bound workloads.

    Prefix caching in brief

    When multiple requests share an identical prefix (common with system prompts or RAG context), vLLM caches the KV blocks for that prefix. Subsequent requests with the same prefix skip the prefill computation entirely.

    Putting It Together¶

    vLLM's design follows a clear principle: treat GPU memory like an OS treats RAM. Fixed-size pages, dynamic allocation, eviction to swap, and iteration-level scheduling together transform LLM serving from a memory-bound afterthought into a throughput engine.

    The inference loop — tokenize, schedule, prefill, decode, sample, stream — runs continuously. Blocks are allocated on demand, freed on completion, and immediately reused. Attention kernels switch between FlashAttention (parallel prefill) and PagedAttention (scattered decode). Under load, mixed batches keep the GPU saturated while new requests flow in without waiting for batch boundaries.

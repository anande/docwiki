    How kubeconfig Is Generated by Kubespray and k3d

    kubeconfig files tell kubectl (and other clients) how to reach a cluster and how to authenticate. By default, kubectl looks for a file named config in ~/.kube/, but tools like Kubespray and k3d generate and manage additional kubeconfigs for the clusters they create.^1^3

    This section explains, in detail, how kubeconfig generation works in Kubespray (Ansible‑based bare‑metal/VM clusters) and k3d (k3s in Docker).

    Common kubeconfig concepts

    • A kubeconfig file is a YAML document containing:
      • clusters: API server endpoints and TLS settings.
      • users: credentials (client certificates, tokens, etc.).
      • contexts: a tuple of (cluster, user, namespace) to make a "profile".
    • kubectl chooses which cluster to talk to based on the current context.
    • You can point kubectl to a specific file by:
      • Setting KUBECONFIG=/path/to/kubeconfig.
      • Using kubectl --kubeconfig=/path/to/kubeconfig ....^4^5

    Kubespray: kubeconfig generation flow

    Kubespray is an Ansible playbook collection that installs a production‑grade Kubernetes cluster on your own hosts. As part of the control‑plane bootstrap, it generates kubeconfig files on the master/control‑plane nodes and optionally on worker nodes.^6^8

    Where kubeconfig lives with Kubespray

    On each control‑plane node, Kubespray (via kubeadm) creates:

    • /etc/kubernetes/admin.conf – admin kubeconfig (cluster‑admin privileges).
    • /etc/kubernetes/kubelet.conf – kubelet client config.
    • /etc/kubernetes/controller-manager.conf, scheduler.conf, etc.

    Kubespray’s documentation calls out that the kubeconfig files it generates generally point to localhost on control‑plane nodes, or to a local nginx proxy / external load balancer if configured.^8

    “The kubeconfig files generated will point to localhost (on kube_control_planes) and kube_node hosts will connect either to a localhost nginx proxy or to a loadbalancer if configured.”^6

    Practically:

    • Control‑plane nodes talk to the API server via https://127.0.0.1:6443 (or a local proxy).
    • Worker nodes may have kubeconfigs that point at:
      • A local nginx proxy on the node, or
      • A dedicated external load balancer fronting multiple API servers.^8

    How Kubespray generates kubeconfig

    The rough flow (simplified) is:

    1. Kubespray runs kubeadm init on the first control‑plane node kubeadm:
      • Generates a CA and server/client certificates.
      • Writes admin.conf and other component configs under /etc/kubernetes/.^9
    2. Ansible templates and copies kubeconfig Kubespray’s Ansible roles:
      • Read admin.conf from /etc/kubernetes/admin.conf.
      • Template or copy kubeconfig files to the appropriate locations on control‑plane and worker nodes.
      • Adjust the server: field to point to either:
        • https://127.0.0.1:6443 (local API), or
        • An HA load balancer fronting the API servers.^6
    3. Optional: expose kubeconfig to the operator machine Common patterns (not automatic unless you script it):
      • Copy /etc/kubernetes/admin.conf from a control‑plane node to your workstation:
    scp ubuntu@cp-1:/etc/kubernetes/admin.conf ~/kubeconfigs/genestack-admin.conf
export KUBECONFIG=~/kubeconfigs/genestack-admin.conf
kubectl get nodes

    - Merge it into your default `~/.kube/config` using `kubectl config` commands.[^2][^4]
    1. Kubespray and “localhost kubeconfig” Since the kubeconfigs generated point at localhost on the control‑plane nodes, when you SSH to a control‑plane node and run:
    export KUBECONFIG=/etc/kubernetes/admin.conf
kubectl get nodes

    it will talk to the API server bound to 127.0.0.1:6443 on that host.^8

    Key characteristics of Kubespray kubeconfig generation

    • Source of truth is the admin.conf produced by kubeadm on the first control‑plane node.^9
    • Transport is https with client certs (cluster‑admin credentials).
    • Endpoints are typically localhost or a configured load balancer, not a public IP directly.^6
    • Distribution to operators is an explicit step (copy the file off the node); Kubespray does not automatically write kubeconfig on your laptop.

    k3d: kubeconfig generation flow

    k3d runs k3s (a lightweight Kubernetes distribution) inside Docker containers. Unlike Kubespray, it has direct control over both the control‑plane and the CLI environment, so it can generate and update kubeconfigs on the fly.^10

    Where kubeconfig lives with k3d

    By default, k3d integrates with your existing kubeconfig:

    • It detects the "default" kubeconfig as either:
      • The file pointed to by KUBECONFIG (if it references exactly one file).
      • Or ~/.kube/config if KUBECONFIG is unset.^11

    k3d can:

    • Write a cluster‑specific kubeconfig under:
      • ~/.k3d/kubeconfig-<cluster-name>.yaml.^11
    • Merge cluster details into your default kubeconfig and optionally switch context.

    How k3d generates kubeconfig during cluster creation

    When you run:

    k3d cluster create mycluster

    the steps are roughly:

    1. k3s server inside Docker creates its own kubeconfig k3s writes a kubeconfig file (usually /etc/rancher/k3s/k3s.yaml inside the container), which points to the cluster’s API endpoint and contains the token/certs.^12
    2. k3d reads that kubeconfig from inside the container
      • It inspects the k3s container.
      • Reads the internal kubeconfig file.
      • Adapts the server: URL to a host‑accessible endpoint (e.g., https://0.0.0.0:<mapped-port> or https://k3d-mycluster-server-0:6443 as seen from your host).^11
    3. k3d either writes or merges kubeconfig on the host

    By default (k3d v5.x+):^11 - k3d cluster create mycluster --kubeconfig-update-default - Merges the new cluster into your default kubeconfig file (~/.kube/config or $KUBECONFIG). - Does not change the current context unless you also pass --kubeconfig-switch-context. - If you don’t disable the default behavior: - A cluster, user, and context entry named something like k3d-mycluster are added to your kubeconfig. - You can list them with:

    kubectl config get-contexts

    k3d also supports: - Writing a standalone kubeconfig file:

    k3d kubeconfig write mycluster

    This creates or updates ~/.k3d/kubeconfig-mycluster.yaml.^11 - Printing a kubeconfig to stdout:

    k3d kubeconfig get mycluster > ./kubeconfig-mycluster.yaml
export KUBECONFIG=./kubeconfig-mycluster.yaml
kubectl get nodes

    ^10

    • Merging into another file after creation:
    k3d kubeconfig merge mycluster --output some/other/file.yaml
# or into default kubeconfig:
k3d kubeconfig merge mycluster --kubeconfig-merge-default

    Add --kubeconfig-switch-context if you want the new cluster to become current.^10

    Example flows with k3d

    1. Default behavior (merge into ~/.kube/config)

    k3d cluster create mycluster
kubectl config get-contexts          # shows context k3d-mycluster
kubectl config use-context k3d-mycluster
kubectl get nodes

    Here, k3d:

    • Pulls the kubeconfig from k3s inside Docker.
    • Merges it into your default kubeconfig.
    • Leaves current context unchanged unless --kubeconfig-switch-context is used.^11

    2. Standalone kubeconfig only

    k3d cluster create mycluster --kubeconfig-update-default=false
k3d kubeconfig write mycluster       # creates ~/.k3d/kubeconfig-mycluster.yaml
export KUBECONFIG=~/.k3d/kubeconfig-mycluster.yaml
kubectl get nodes

    This isolates the cluster config in a dedicated file, which is often useful for scripting or demos.^10

    Key characteristics of k3d kubeconfig generation

    • Automatic: k3d always has a kubeconfig for each cluster and can either:
      • Merge it into your main kubeconfig, or
      • Write it separately under ~/.k3d/.^11
    • Context management:
      • Creation can update default kubeconfig and optionally switch context via --kubeconfig-switch-context.^10
    • Host‑visible endpoint:
      • It rewrites the server: URL from the k3s internal one to a host‑reachable address/port.

    Summary: Kubespray vs k3d kubeconfig behavior

    Aspect Kubespray k3d
    Primary environment Bare‑metal/VM hosts, often in clouds or on‑prem k3s inside Docker on local/development machines
    Where kubeconfig is created /etc/kubernetes/admin.conf on control‑plane nodes via kubeadm Inside k3s server container, then exported to host
    Default kubeconfig endpoint https://127.0.0.1:6443 or local nginx / LB on the nodes Host‑reachable API endpoint (mapped Docker port)
    How operator gets kubeconfig Manual copy from node, then KUBECONFIG or merge into ~/.kube/config Automatically merged into or written alongside your default kubeconfig
    Integration with ~/.kube/config Not automatic; you decide how/where to merge Automatic (unless disabled), with options to merge or write standalone files
    Context switching Manual via kubectl config use-context Optional automatic switch via --kubeconfig-switch-context during merge/write

    Both tools ultimately produce standard kubeconfig files; the main differences are where the files originate and how much automation they provide for placing and merging them into your local configuration.^6

    Bulletproof RHOSO: Performance Tuning and Security Hardening Guide¶

    A comprehensive, parameter-level reference for building the most optimal and secure Red Hat OpenStack Services on OpenShift (RHOSO) 18.0 cluster. Every recommendation maps back to a specific component or flow from the 96-scenario FlowStory Visualizer — so you can see exactly where each tuning knob takes effect in the architecture.

    This guide covers four performance domains — Compute, Network, Storage, and API/Control Plane — plus a full Security Hardening section and an Observability section. It concludes with a quick-reference cheat sheet.

    Sources: RHOSO 18.0 Product Docs, RHOSO 18.0 Hardening Guide, upstream OpenStack docs, Ceph tuning community guides, and the openstack-discuss mailing list.

    1. Compute Performance¶

    Relevant flows: VM Launch (1), Live Migration (2), VM Resize (20), NUMA-Aware VM (85), Hugepages + RT Kernel (86), Multi-GPU MIG (90)

    CPU Pinning and NUMA Topology¶

    CPU pinning eliminates scheduler jitter by locking each vCPU to a physical core. Without it, the kernel can migrate vCPU threads across sockets, causing cache misses and cross-NUMA memory access penalties.

    Create a ConfigMap for your EDPM compute nodes:

    apiVersion: v1
kind: ConfigMap
metadata:
  name: nova-cpu-pinning
  namespace: openstack
data:
  25-nova-cpu-pinning.conf: |
    [compute]
    cpu_dedicated_set = 4-31,36-63
    cpu_shared_set = 2-3,34-35
    [DEFAULT]
    reserved_host_memory_mb = 4096
    reserved_huge_pages = node:0,size:1GB,count:64
    reserved_huge_pages = node:1,size:1GB,count:64

    Then create a dedicated CPU pinning flavor:

    openstack flavor create m1.pinned --vcpus 4 --ram 8192 --disk 40
openstack flavor set m1.pinned \
  --property hw:cpu_policy=dedicated \
  --property hw:cpu_thread_policy=require \
  --property hw:emulator_threads_policy=isolate \
  --property hw:mem_page_size=1GB \
  --property hw:numa_nodes=1

    Emulator thread isolation

    Setting hw:emulator_threads_policy=isolate moves QEMU I/O threads, timers, and signal handlers onto the cpu_shared_set cores instead of competing with vCPU threads. This alone can improve VM latency by 15-30% for CPU-bound workloads.

    Kernel and Host-Level Tuning¶

    Apply the cpu-partitioning tuned profile to isolate cores from the kernel scheduler:

    # In OpenStackDataPlaneNodeSet spec
nodeTemplate:
  ansible:
    ansibleVars:
      edpm_tuned_profile: cpu-partitioning
      edpm_tuned_isolated_cores: "4-31,36-63"

    Additional kernel boot parameters for NFV/telco workloads (Flow 86):

    default_hugepagesz=1G hugepagesz=1G hugepages=128
isolcpus=4-31,36-63
nohz_full=4-31,36-63
rcu_nocbs=4-31,36-63
intel_pstate=disable
processor.max_cstate=0
intel_idle.max_cstate=0

    KVM and Libvirt Tuning¶

    Parameter Recommended Why
    vhost_net module Loaded Offloads virtio-net processing from QEMU to kernel, reducing CPU overhead
    ksm (Kernel Same-page Merging) Disabled for pinned workloads KSM scanning steals CPU cycles; only enable for overcommitted shared workloads
    cpu_mode host-passthrough Exposes all host CPU features to VMs for maximum performance
    cpu_model_extra_flags Set per fleet Add +pcid,+spec-ctrl for security, ensure uniformity for live migration
    rx/tx queue sizes 1024 virtio-net queue depth; reduces packet drops under burst

    Live migration compatibility

    Using host-passthrough maximises performance but requires identical CPU models across all computes in a migration domain. Use cpu_model_extra_flags to establish a common baseline if your fleet has mixed CPU generations.

    2. Network Performance¶

    Relevant flows: Network + Router + FIP (4), Provider Net Bridge Detail (11), VM-to-VM Ping (12), Floating IP DNAT/SNAT (14), SR-IOV (62), BGP EVPN (81), DPDK OVS (82), OVN HW Offload (84)

    MTU and Jumbo Frames¶

    Geneve encapsulation adds ~58 bytes of overhead. Fragmentation kills throughput.

    Layer MTU Setting Value
    Physical NIC mtu 9000
    Geneve overlay (OVN) Cluster network MTU 8900 (NIC MTU - 100)
    VM internal Guest MTU 8900 or 1500 (DHCP-advertised) 
    # On EDPM compute nodes
ip link set dev ens3f0 mtu 9000
ip link set dev ens3f1 mtu 9000

# OVN will auto-set Geneve tunnel MTU based on physical MTU

    Geneve Offload¶

    Modern NICs can offload Geneve encapsulation and checksum to hardware, freeing CPU for VM workloads:

    # Verify offload support
ethtool -k ens3f0 | grep -i geneve
#   tx-udp_tnl-segmentation: on
#   tx-udp_tnl-csum-segmentation: on

# Enable if disabled
ethtool -K ens3f0 tx-udp_tnl-segmentation on
ethtool -K ens3f0 tx-udp_tnl-csum-segmentation on

    OVN Hardware Offload with DPU/SmartNIC (Flow 84)¶

    For 100Gbps line-rate with zero host CPU cost, configure SR-IOV in switchdev mode on NVIDIA ConnectX-5+ or BlueField DPUs:

    apiVersion: sriovnetwork.openshift.io/v1
kind: SriovNetworkNodePolicy
metadata:
  name: ovn-hw-offload
spec:
  resourceName: ovn_offload
  nodeSelector:
    feature.node.kubernetes.io/network-sriov.capable: "true"
  numVfs: 16
  nicSelector:
    vendor: "15b3"
  deviceType: netdevice
  eSwitchMode: switchdev

    OVN flows are offloaded to the NIC via TC flower rules. Verify with:

    tc filter show dev representor0
# Look for 'in_hw' and 'in_hw_count' labels

    What gets offloaded

    Geneve encap/decap, checksums, and L2/L3 forwarding are offloaded. NAT, conntrack, and complex ACLs typically remain in software.

    DPDK-Accelerated OVS for NFV (Flow 82)¶

    DPDK replaces kernel-space packet processing with userspace poll-mode drivers, achieving 10x throughput:

    # /etc/sysconfig/openvswitch (EDPM node)
OVS_USER_ID="openvswitch:hugetlbfs"

# OVS-DPDK configuration
ovs-vsctl set Open_vSwitch . other_config:dpdk-init=true
ovs-vsctl set Open_vSwitch . other_config:dpdk-lcore-mask=0x3
ovs-vsctl set Open_vSwitch . other_config:pmd-cpu-mask=0x3C
ovs-vsctl set Open_vSwitch . other_config:dpdk-socket-mem="4096,4096"

    OVS and OVN Database Tuning¶

    # Increase flow revalidation timeout (reduces CPU on busy nodes)
ovs-vsctl set Open_vSwitch . other_config:max-revalidator=10000

# OVN: increase OVSDB probe interval for large clusters (>50 nodes)
# Prevents false leader failovers during control plane load spikes
ovs-vsctl set Open_vSwitch . external-ids:ovn-openflow-probe-interval=60
ovs-vsctl set Open_vSwitch . external-ids:ovn-remote-probe-interval=60000

    Network Separation¶

    Dedicate NICs or bonds per traffic type to prevent contention:

    Network Purpose Bandwidth
    ctlplane OpenShift API, EDPM management 10GbE
    internalapi OpenStack inter-service RPC 25GbE
    tenant VM overlay (Geneve) 25GbE+
    storage Ceph public network 25GbE+
    storagemgmt Ceph cluster (replication) 25GbE+
    external Floating IPs, provider nets 25GbE+

    3. Storage Performance¶

    Relevant flows: Volume Create + Attach (5), Cinder Snapshot + Clone (24), Volume Live Extend (25), Rook-Ceph Lifecycle (39-57), EC Pool (77), Encryption at Rest (78), NVMe-oF Gateway (80)

    Ceph OSD Tuning¶

    # ceph.conf [osd] section
[osd]
osd_memory_target = 8589934592          # 8 GB minimum per OSD
bluestore_cache_autotune = true
bluestore_cache_size_ssd = 4294967296   # 4 GB for SSD/NVMe
osd_recovery_max_active = 3            # Limit recovery I/O
osd_max_backfills = 1                   # One backfill per OSD at a time
bluestore_compression_mode = passive    # Only compress if client requests it
bluestore_compression_algorithm = snappy

    RBD Client Cache on Compute Nodes¶

    Enable writeback caching on the librbd client for a 2-4x improvement in write latency:

    # /etc/ceph/ceph.conf on compute nodes
[client]
rbd_cache = true
rbd_cache_size = 134217728              # 128 MB
rbd_cache_max_dirty = 100663296         # 96 MB
rbd_cache_target_dirty = 67108864       # 64 MB
rbd_cache_max_dirty_age = 5
rbd_cache_writethrough_until_flush = true

    Then set Nova's disk cache mode to take advantage of it:

    # nova.conf on compute nodes
[libvirt]
disk_cachemodes = network=writeback
images_type = rbd

    Data safety

    writeback caching means dirty data can be lost on compute node crash. The rbd_cache_writethrough_until_flush = true setting uses write-through until the first guest flush, providing a safety net during boot. For databases and other fsync-heavy workloads, guests should use O_DIRECT or O_SYNC which bypass the cache.

    Linux Kernel Tuning for Ceph Nodes¶

    # CPU governor — eliminate latency spikes during I/O bursts
echo performance | tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor

# Disable Transparent Huge Pages — THP + tcmalloc causes OSD memory bloat
echo never > /sys/kernel/mm/transparent_hugepage/enabled
echo never > /sys/kernel/mm/transparent_hugepage/defrag

# Swappiness — prevent OSD stalling from page-outs
echo 0 > /proc/sys/vm/swappiness

# NVMe I/O scheduler — NVMe has hardware queues, kernel scheduling adds overhead
for dev in /sys/block/nvme*/queue/scheduler; do
  echo none > "$dev"
done

# Disable CPU deep idle states
for cpu in /sys/devices/system/cpu/cpu*/cpuidle/state[2-9]/disable; do
  echo 1 > "$cpu" 2>/dev/null
done

    NUMA Pinning for OSDs¶

    # Verify NVMe and NIC are on the same NUMA node
cat /sys/block/nvme0n1/device/numa_node   # Should match
cat /sys/class/net/ens3f0/device/numa_node # Should match

# Pin OSD to matching NUMA node via systemd override
# /etc/systemd/system/ceph-osd@0.service.d/numa.conf
[Service]
CPUAffinity=0-31
ExecStart=
ExecStart=/usr/bin/numactl --cpunodebind=0 --membind=0 /usr/bin/ceph-osd -f --id %i

    Network Tuning for Ceph¶

    # Expand socket buffers for bursty replication I/O
sysctl -w net.core.rmem_max=67108864
sysctl -w net.core.wmem_max=67108864
sysctl -w net.ipv4.tcp_rmem="4096 87380 33554432"
sysctl -w net.ipv4.tcp_wmem="4096 65536 33554432"

# Keep congestion window warm between bursts
sysctl -w net.ipv4.tcp_slow_start_after_idle=0

# Wide ephemeral port range for high OSD connection counts
sysctl -w net.ipv4.ip_local_port_range="1024 65535"
sysctl -w net.core.somaxconn=65535

# Jumbo frames on Ceph cluster network
ip link set dev ens3f1 mtu 9000

    CRUSH Rules and Pool Strategy¶

    Pool Type Use Case CRUSH Rule Efficiency
    3x Replicated Boot volumes, Galera, RabbitMQ rack-failure-domain 33% raw utilisation
    EC 4+2 Cold data, backups, RGW objects host-failure-domain 67% raw utilisation
    EC 8+3 Large-scale archive rack-failure-domain 73% raw utilisation 
    # Create rack-aware replicated rule
ceph osd crush rule create-replicated ssd-rack default rack ssd

# Create EC profile and pool
ceph osd erasure-code-profile set ec-42 k=4 m=2 crush-failure-domain=host
ceph osd pool create ec-cold-data 128 128 erasure ec-42

    4. API and Control Plane Performance¶

    Relevant flows: EDPM Node Deploy (3), Control Plane Upgrade (6), Keystone Federation (27), Heat Stack Create (30), API Tracing (36), Quota Enforcement (38)

    Keystone Token Caching¶

    # keystone.conf via OpenStackControlPlane customServiceConfig
[cache]
enabled = true
backend = oslo_cache.memcache_pool
memcache_servers = memcached-0.memcached:11211,memcached-1.memcached:11211

[token]
expiration = 3600
cache_time = 3600
provider = fernet

[memcache]
memcache_security_strategy = ENCRYPT
memcache_secret_key = <generated-key>

    Token cache hit rate

    With caching enabled and cache_time set to match expiration, token validation becomes a local memcached lookup instead of a database query. This can reduce Keystone DB load by 90%+ in high-traffic environments.

    Nova Concurrency (2026.1 Gazpacho+)¶

    Nova has transitioned from Eventlet green threads to native OS threading. Tune thread pools based on service role:

    Service executor_thread_pool_size Notes
    nova-conductor 64-128 Handles DB proxy for all computes + scheduler; scale horizontally
    nova-scheduler 32-64 Receives placement queries; memory-intensive
    nova-api 32-64 Matches osapi_compute_workers (typically = CPU cores)
    nova-compute 16-32 Handles lifecycle RPC from API + migration from peers 
    # nova.conf
[DEFAULT]
osapi_compute_workers = 16
metadata_workers = 4

[conductor]
workers = 8

[scheduler]
workers = 4

    RabbitMQ¶

    # oslo_messaging_rabbit section in each service's config
[oslo_messaging_rabbit]
rabbit_quorum_queue = true
rabbit_transient_quorum_queue = true
use_queue_manager = true
rabbit_stream_fanout = true
rabbit_qos_prefetch_count = 1
heartbeat_timeout_threshold = 60
heartbeat_rate = 2

    SSD required for quorum queues

    Quorum queues use the Raft consensus algorithm and are write-heavy. RabbitMQ on HDD can see throughput drop 50%+ under mixed workloads. Use SSD-backed storage for all RabbitMQ nodes.

    MariaDB Galera¶

    # Galera tuning
[mysqld]
innodb_buffer_pool_size = 32G          # 50-75% of available RAM
innodb_buffer_pool_instances = 16      # Divide into subpools >= 1GB each
innodb_log_file_size = 1G             # Accommodate high write volumes
innodb_flush_method = O_DIRECT
innodb_flush_log_at_trx_commit = 2    # Flush once per second, not per commit
innodb_io_capacity = 10000            # Match SSD IOPS capability
innodb_read_io_threads = 8
innodb_write_io_threads = 8
max_connections = 4096
query_cache_size = 0                  # Disable — known bottleneck
query_cache_type = 0
thread_cache_size = 64
table_open_cache = 4096

# Galera/wsrep
wsrep_slave_threads = 16              # Match CPU core count
wsrep_provider_options = "gcache.size=10G; gcache.page_size=10G"
wsrep_sst_method = mariabackup

    Write routing

    Galera is multi-master but all writes should be routed to a single primary node via HAProxy or ProxySQL. Multi-node writes cause certification conflicts and rollbacks that degrade performance. HAProxy operates at L4 (TCP), so it cannot separate read/write queries — for true read/write splitting, use ProxySQL or MaxScale.

    5. Security Hardening¶

    Relevant flows: Keystone Federation (27), TLS Certificate Lifecycle (28), Barbican + Volume Encryption (29), Centralized Logging (65), Compliance Scan (66), Audit Tracking (67), External Secrets (68), IDM LDAP (74), IDM CA (75), SSSD + HBAC (76), Tenant Isolation (95)

    This section draws from the RHOSO 18.0 Hardening Guide.

    Identity and Access Control¶

    Secure RBAC (SRBAC) is enabled by default in RHOSO 18.0 with three personas:

    Persona System Scope Project Scope
    admin Full cluster management Full project management
    member — Create/manage own resources
    reader Read-only cluster view Read-only project view

    Fernet key rotation is automated. Tune frequency and key count:

    # OpenStackControlPlane CR
spec:
  keystone:
    template:
      fernetRotationDays: 1
      fernetMaxActiveKeys: 5

    PCI-DSS compliance settings:

    # keystone customServiceConfig
[security_compliance]
lockout_failure_attempts = 5
lockout_duration = 1800
unique_last_password_count = 5
minimum_password_age = 86400
password_expires_days = 90
password_regex = ^(?=.*\d)(?=.*[a-z])(?=.*[A-Z])(?=.*[!@#$%^&*]).{12,}$
password_regex_description = Must be 12+ chars with upper, lower, digit, special
change_password_upon_first_use = true
disable_user_account_days_inactive = 90

    Federation with Red Hat IDM (Flows 74-76):

    • Configure Keystone LDAP domain backend pointing to FreeIPA
    • Enable Kerberos SSO via kinit for seamless auth
    • Deploy SSSD + HBAC rules on EDPM nodes for host-based access control
    • Use IDM Dogtag CA as the enterprise PKI for all RHOSO TLS certificates

    Encryption¶

    TLS Everywhere (TLS-e) is enabled by default and cannot be disabled in RHOSO 18.0. It covers:

    • Ingress (public API endpoints) via OpenShift Routes
    • Internal pod-to-pod communication via cert-manager re-encryption
    • EDPM node communication via custom certificates

    Volume encryption with Barbican (Flow 29):

    # Create encrypted volume type
openstack volume type create encrypted-volumes
openstack volume type set encrypted-volumes \
  --encryption-provider luks \
  --encryption-cipher aes-xts-plain64 \
  --encryption-key-size 256 \
  --encryption-control-location front-end

    Ceph encryption at rest (Flow 78):

    # Enable dm-crypt for all new OSDs
ceph config set osd osd_dmcrypt_type luks2
# Deploy with encryption
ceph orch apply osd --all-available --method raw --dmcrypt

    Memcached authentication:

    # Prevent unauthorised cache poisoning
[cache]
memcache_security_strategy = ENCRYPT
memcache_secret_key = <strong-random-key>

    Network Security¶

    Control plane — Kubernetes NetworkPolicies restrict inter-pod traffic:

    apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: restrict-openstack-ns
  namespace: openstack
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: openstack
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: openstack
    - to:
        - ipBlock:
            cidr: 0.0.0.0/0
      ports:
        - protocol: TCP
          port: 443

    Tenant isolation — OVN ACLs implement zero-trust microsegmentation:

    • Security groups (port-level stateful firewall) are implemented as OVN ACLs and Port Groups
    • FWaaS v2 provides North-South perimeter control at the router level
    • Ports with no security group get a default-drop ACL (neutron_pg_drop)

    Data plane hardening:

    # EDPM nodes — disable password SSH, enforce key-only
sed -i 's/^#PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
sed -i 's/^#PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config
systemctl restart sshd

# SELinux — must be enforcing
getenforce  # Should return "Enforcing"

# Firewalld — restrict to required ports only
firewall-cmd --permanent --add-service=ssh
firewall-cmd --permanent --add-port=6081/udp   # Geneve
firewall-cmd --permanent --add-port=6641/tcp   # OVN SB
firewall-cmd --permanent --add-port=6642/tcp   # OVN NB
firewall-cmd --reload

    6. Observability as a Performance Lever¶

    Relevant flows: API Tracing (36), Split-Brain Detection (37), Ceph Dashboard + Prometheus (53), Centralized Logging (65)

    Observability is not a nice-to-have — it is the mechanism by which you detect and prevent performance degradation before users notice.

    Critical Metrics to Monitor¶

    Component Metric Alert Threshold What It Means
    RabbitMQ Queue depth per service > 1000 messages Consumer is overwhelmed or dead
    RabbitMQ messages_unacknowledged > 500 Prefetch or processing bottleneck
    Galera wsrep_flow_control_paused > 0.0 Cluster is throttling writes; add slave threads or improve I/O
    Galera wsrep_local_recv_queue_avg > 0.5 Node falling behind replication
    Ceph osd_op_latency p99 > 50ms (SSD) OSD outlier or NUMA misalignment
    Ceph osd_apply_latency p99 > 100ms Disk or network bottleneck
    Ceph PG state != active+clean Any degraded PGs Trigger investigation
    Nova Scheduler select_destinations time > 2s Placement DB query slow or filter chain too long
    Nova nova_running_vms vs nova_vcpus_available > 85% utilisation Capacity planning trigger
    Keystone Token issuance latency > 500ms Memcached miss or DB contention
    OVN ovn-controller restart count > 0 in 1h Connection instability or leader failover

    Observability Stack¶

    Prometheus (ServiceMonitor CRs)
    ├── Ceph MGR prometheus module  →  ceph_osd_*, ceph_pool_*, ceph_pg_*
    ├── RabbitMQ exporter           →  rabbitmq_queue_*, rabbitmq_connections
    ├── MySQL/Galera exporter       →  mysql_global_status_wsrep_*
    └── OpenStack exporters         →  nova_*, neutron_*, keystone_*

Vector (DaemonSet)
    ├── Pod logs (stdout/stderr)
    ├── EDPM syslog (rsyslog → Vector)
    └── → Loki → Grafana LogQL

Jaeger (Distributed Tracing)
    └── X-Trace-Info headers in API calls → per-service spans → waterfall view

    Every metric needs a runbook

    An alert without a documented response procedure is just noise. For each threshold above, document: (1) what to check first, (2) how to confirm the root cause, (3) the remediation steps.
